zugferd-validator

Parse and validate ZUGFeRD/Factur-X e-invoices — profile detection, an EN 16931-mapped arithmetic check suite, and IBAN validation. Pure TypeScript, runs anywhere Node or a bundler does.

Usage

Parse the CII XML embedded in a ZUGFeRD/Factur-X PDF (or a standalone XRechnung XML), then run the check suite against it.

import { parseCiiXml, runChecks, parseAmount } from 'zugferd-validator'

const invoice = parseCiiXml(xmlString)

const findings = runChecks(invoice, {
  tolerance: parseAmount('0.01')!, // a Money value, not a plain number
  // pdfText: extractedPdfText,    // optional -- enables R-PDF-01/02/03
})

for (const finding of findings) {
  console.log(finding.ruleId, finding.severity, finding.messageDe)
}

parseCiiXml throws on structurally malformed XML — missing required fields, an unsupported date format, no rsm:CrossIndustryInvoice root. Wrap it in a try/catch if the input isn't already known-good.

MINIMUM and BASIC WL ZUGFeRD profiles carry no line items — runChecks already filters out line-item/VAT-breakdown-dependent rules for those via invoice.capabilities, so you don't need to special-case it.

Rule catalogue

13 rules, each a pure function of (invoice, ctx) → Finding[], mapped to their EN 16931 business rule where one exists. Available at runtime as rules (id, description, and gating flags included).

R-PDF-01/02/03 cross-check invoice values against the PDF's visible text, if you pass pdfText — extract that however you like (pdf.js, a Python PDF library, your own pipeline); this package has no opinion on how you got the text, only on what it's checked against. Finding.messageDe is German — see Known limitations.

Known limitations

  • German-only messages. Finding.messageDe is German-language text — the domain vocabulary (Rechnungsnummer, Steuersatz, etc.) is inherently German. Not internationalized; ruleId and severity are stable, locale-independent fields if you need to build your own messages.
  • Not full EN 16931 conformance validation. This checks internal arithmetic consistency — does the invoice add up to itself — not full standard conformance. See the KoSIT validator for that.
  • IBAN shape, not per-country length. Checksum (ISO 7064 MOD-97-10) and general shape (ISO 13616) are validated, not the exact BBAN length per country — a 34+-country length table is real external data with its own maintenance surface.

API reference

Grouped the same way as the package's public barrel (src/index.ts) — everything here is a named export from 'zugferd-validator'.

Parsing & profile

functionparseCiiXml(xml: string): Invoice

Parses CII XML (the format embedded in ZUGFeRD/Factur-X, or standalone XRechnung) into a typed Invoice. Throws on malformed input.

functiondetectProfile(guidelineId?: string): { profile: ZugferdProfile; capabilities: ProfileCapabilities }

Classifies the ZUGFeRD/Factur-X guideline URN into a profile and its capability flags (line items? VAT breakdown? payment terms?). Called internally by parseCiiXml; exported for standalone use.

functionunitLabel(unitCode: string): string

UN/ECE Rec. 20 unit code → German display label (MTQ → "m³", TNE → "t", …). Falls back to the raw code for anything not in the table.

Checks

functionrunChecks(invoice: Invoice, ctx: CheckContext): Finding[]

Runs every rule whose gating flags the invoice's capabilities satisfy, and flattens their findings. This is the one function you need for "give me every problem with this invoice."

construles: RuleEntry[]

The full rule catalogue (see above) as data — each entry carries id, the underlying rule function, a German descriptionDe, an optional EN 16931 businessRule code, and the requiresLineItems / requiresVatBreakdown gating flags runChecks filters on.

typeFinding, Severity, FindingTarget, CheckContext, Rule

Severity is 'error' | 'warning' | 'info' — a difference beyond your tolerance is an error, within it a warning. CheckContext is { tolerance: Money; pdfText?: string }. Rule is the function shape every entry in rules implements: (invoice, ctx) => Finding[].

Domain types

typeInvoice

profile, capabilities, invoiceNumber, issueDate, currency, seller/buyer (Party), lines (InvoiceLine[], empty for MINIMUM/BASIC WL), vatBreakdown (VatBreakdownEntry[]), totals (InvoiceTotals), optional paymentTermsText and iban.

Also exported: InvoiceLine, Party, VatBreakdownEntry, InvoiceTotals, ZugferdProfile, ProfileCapabilities — the full shapes are in the source.

Money

Amounts are big.js Big instances throughout, never plain number — CII unit prices can carry four decimal places, and integer cents can't represent €0.0375 per unit without a second scaling concept.

typeMoney, Quantity

Both are aliases for Big. Money for amounts, Quantity for billed/basis quantities — same underlying type, named for what they mean at each call site.

functionparseAmount(raw: string | undefined): Money | null

The only sanctioned way to construct a Money value from outside the package — there's no re-exported Big constructor. Returns null for undefined, empty, or unparseable input.

functionadd(...values: Money[]): Money · multiply(a, b): Money · round2(value): Money · equalWithin(a, b, tolerance): boolean

round2 is half-up ("kaufmännisch") — EN 16931 doesn't mandate a rounding method, so this is a documented choice, not an assumption.

functionformatEUR(value: Money): string · formatQuantity(value: Quantity): string

German/Austrian locale formatting — formatEUR → "1.234,56 €", formatQuantity → thousands-separated with a decimal comma, no forced decimals for whole numbers.

IBAN

functionisValidIban(iban: string): boolean

ISO 7064 MOD-97-10 checksum + general ISO 13616 shape (2-letter country code, 2 check digits, 11–30 alphanumerics) — not a per-country exact-length table; see limitations.

functionformatIban(iban: string): string

Groups into blocks of 4 for display, the way IBANs are conventionally printed: DE89 3704 0044 0532 0130 00.
